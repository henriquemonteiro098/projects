# Mock banking database project

> Study document for practice with GitHub Copilot in VS Code.
>
> This project is purely educational and simulated. It does not handle real money, does not replace a banking system, and should not be used in production without security audits, privacy reviews, and regulatory compliance.

## 1. Objective

Translate concepts from study notes on the time value of money into a simple PostgreSQL database, allowing users to register clients, manage accounts, track balances, and record transfers.

The system helps study:

- Inflation, purchasing power, and real yield.
- The difference between saving money and using a financial product.
- Simple and compound interest simulations.
- Balances, inflows, outflows, and transfers.
- Referential integrity and SQL transactions.
- Basic security practices.

The system does not provide investment recommendations, does not identify the "best investment", and does not use real-world yields as financial guarantees.

## 2. Initial scope

### User registration

- `nome` (user name)
- `email` (user email)
- `senha_hash` (password hash, stored only as a cryptographic hash, never in plain text)

### Financial records

- Bank accounts tied to users.
- Stored balance (`saldo`).
- Historical logs for deposits and withdrawals.
- Transfer history between accounts.
- Description and status for each transaction.
- Optional compound interest simulations, kept separate from actual account balances.

## 3. Modeling decisions

1. A single user can hold one or more bank accounts.
2. Balances are never modified directly through manual edits. They must be updated through ledger operations within a transaction.
3. Every transfer records an origin account and a destination account.
4. Transfers to the same account are blocked.
5. Every transaction amount must be greater than zero.
6. Passwords are never stored in plain text. The database receives a secure hash generated by the backend (e.g., Argon2 or bcrypt).
7. `NUMERIC(14,2)` is used for monetary values instead of floating-point types (`FLOAT` or `DOUBLE`).
8. The database enforces `CHECK`, `UNIQUE`, foreign keys, and transactions to safeguard data integrity.
9. Movement tables act as immutable ledgers. A transfer is never deleted to adjust a balance; in real production systems, corrections require reversal entries and audit trails.

## 4. Entity relationships

```text
usuarios 1 ─── N contas
contas   1 ─── N movimentacoes
contas   1 ─── N transferencias (as origin)
contas   1 ─── N transferencias (as destination)
usuarios 1 ─── N simulacoes_juros
```

## 5. Database structure

Create a file named `01_schema.sql` and run it in a local PostgreSQL instance:

```sql
CREATE DATABASE banco_ficticio;
```

After connecting to the `banco_ficticio` database, run the following DDL script:

```sql
CREATE TABLE usuarios (
    id BIGSERIAL PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    email VARCHAR(254) NOT NULL UNIQUE,
    senha_hash VARCHAR(255) NOT NULL,
    ativo BOOLEAN NOT NULL DEFAULT TRUE,
    criado_em TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    atualizado_em TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT ck_usuario_nome CHECK (length(trim(nome)) >= 2),
    CONSTRAINT ck_usuario_email CHECK (position('@' IN email) > 1)
);

CREATE TABLE contas (
    id BIGSERIAL PRIMARY KEY,
    usuario_id BIGINT NOT NULL REFERENCES usuarios(id) ON DELETE RESTRICT,
    numero VARCHAR(20) NOT NULL UNIQUE,
    tipo VARCHAR(20) NOT NULL DEFAULT 'corrente',
    saldo NUMERIC(14,2) NOT NULL DEFAULT 0,
    moeda CHAR(3) NOT NULL DEFAULT 'BRL',
    ativa BOOLEAN NOT NULL DEFAULT TRUE,
    criada_em TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT ck_conta_tipo CHECK (tipo IN ('corrente', 'poupanca', 'estudo')),
    CONSTRAINT ck_conta_saldo CHECK (saldo >= 0),
    CONSTRAINT ck_conta_moeda CHECK (moeda = 'BRL')
);

CREATE TABLE movimentacoes (
    id BIGSERIAL PRIMARY KEY,
    conta_id BIGINT NOT NULL REFERENCES contas(id) ON DELETE RESTRICT,
    tipo VARCHAR(20) NOT NULL,
    valor NUMERIC(14,2) NOT NULL,
    saldo_apos NUMERIC(14,2) NOT NULL,
    descricao VARCHAR(255),
    criado_em TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT ck_movimentacao_tipo CHECK (tipo IN ('deposito', 'retirada', 'transferencia_entrada', 'transferencia_saida')),
    CONSTRAINT ck_movimentacao_valor CHECK (valor > 0),
    CONSTRAINT ck_movimentacao_saldo CHECK (saldo_apos >= 0)
);

CREATE TABLE transferencias (
    id BIGSERIAL PRIMARY KEY,
    conta_origem_id BIGINT NOT NULL REFERENCES contas(id) ON DELETE RESTRICT,
    conta_destino_id BIGINT NOT NULL REFERENCES contas(id) ON DELETE RESTRICT,
    valor NUMERIC(14,2) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'concluida',
    descricao VARCHAR(255),
    criada_em TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    concluida_em TIMESTAMPTZ,
    CONSTRAINT ck_transferencia_contas_diferentes CHECK (conta_origem_id <> conta_destino_id),
    CONSTRAINT ck_transferencia_valor CHECK (valor > 0),
    CONSTRAINT ck_transferencia_status CHECK (status IN ('pendente', 'concluida', 'cancelada'))
);

CREATE TABLE simulacoes_juros (
    id BIGSERIAL PRIMARY KEY,
    usuario_id BIGINT NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
    valor_inicial NUMERIC(14,2) NOT NULL,
    taxa_mensal NUMERIC(8,5) NOT NULL,
    quantidade_meses INTEGER NOT NULL,
    regime VARCHAR(12) NOT NULL,
    valor_final NUMERIC(14,2) NOT NULL,
    criada_em TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT ck_simulacao_valor CHECK (valor_inicial > 0),
    CONSTRAINT ck_simulacao_taxa CHECK (taxa_mensal >= 0),
    CONSTRAINT ck_simulacao_meses CHECK (quantidade_meses > 0),
    CONSTRAINT ck_simulacao_regime CHECK (regime IN ('simples', 'compostos')),
    CONSTRAINT ck_simulacao_valor_final CHECK (valor_final >= valor_inicial)
);

CREATE INDEX idx_contas_usuario_id ON contas(usuario_id);
CREATE INDEX idx_movimentacoes_conta_id_data ON movimentacoes(conta_id, criado_em DESC);
CREATE INDEX idx_transferencias_origem ON transferencias(conta_origem_id, criada_em DESC);
CREATE INDEX idx_transferencias_destino ON transferencias(conta_destino_id, criada_em DESC);
CREATE INDEX idx_transferencias_status ON transferencias(status);
CREATE INDEX idx_simulacoes_usuario_id ON simulacoes_juros(usuario_id);
```

## 7. Basic operations

### Create a deposit

```sql
BEGIN;

UPDATE contas
SET saldo = saldo + 200.00
WHERE id = 1 AND ativa = TRUE;

INSERT INTO movimentacoes (conta_id, tipo, valor, saldo_apos, descricao)
SELECT id, 'deposito', 200.00, saldo, 'Study deposit'
FROM contas
WHERE id = 1;

COMMIT;
```

### Create a withdrawal with validation

```sql
BEGIN;

UPDATE contas
SET saldo = saldo - 100.00
WHERE id = 1
  AND ativa = TRUE
  AND saldo >= 100.00;

-- The backend must verify that exactly one row was updated.
-- If zero rows updated, run ROLLBACK: insufficient balance or invalid account.

INSERT INTO movimentacoes (conta_id, tipo, valor, saldo_apos, descricao)
SELECT id, 'retirada', 100.00, saldo, 'Study withdrawal'
FROM contas
WHERE id = 1;

COMMIT;
```

### Safe transfer between two accounts

The transfer must execute inside a single transaction. The application verifies updated row counts on each step, rolling back if any check fails.

```sql
BEGIN;

-- Lock rows to prevent race conditions during concurrent operations
SELECT id, saldo
FROM contas
WHERE id IN (1, 2)
ORDER BY id
FOR UPDATE;

UPDATE contas
SET saldo = saldo - 75.50
WHERE id = 1
  AND ativa = TRUE
  AND saldo >= 75.50;

UPDATE contas
SET saldo = saldo + 75.50
WHERE id = 2
  AND ativa = TRUE;

INSERT INTO transferencias (
    conta_origem_id,
    conta_destino_id,
    valor,
    status,
    descricao,
    concluida_em
)
VALUES (1, 2, 75.50, 'concluida', 'Study transfer', NOW());

INSERT INTO movimentacoes (conta_id, tipo, valor, saldo_apos, descricao)
SELECT id, 'transferencia_saida', 75.50, saldo, 'Transfer to account 2'
FROM contas WHERE id = 1;

INSERT INTO movimentacoes (conta_id, tipo, valor, saldo_apos, descricao)
SELECT id, 'transferencia_entrada', 75.50, saldo, 'Transfer from account 1'
FROM contas WHERE id = 2;

COMMIT;
```

## 8. Practice queries

### Users and accounts

```sql
SELECT
    u.nome,
    u.email,
    c.numero,
    c.tipo,
    c.saldo,
    c.moeda
FROM usuarios u
JOIN contas c ON c.usuario_id = u.id
WHERE u.ativo = TRUE
ORDER BY u.nome;
```

### Account transaction history

```sql
SELECT
    m.criado_em,
    m.tipo,
    m.valor,
    m.saldo_apos,
    m.descricao
FROM movimentacoes m
WHERE m.conta_id = 1
ORDER BY m.criado_em DESC, m.id DESC;
```

### Sent and received transfers

```sql
SELECT
    t.id,
    origem.numero AS conta_origem,
    destino.numero AS conta_destino,
    t.valor,
    t.status,
    t.criada_em,
    t.descricao
FROM transferencias t
JOIN contas origem ON origem.id = t.conta_origem_id
JOIN contas destino ON destino.id = t.conta_destino_id
WHERE t.conta_origem_id = 1
   OR t.conta_destino_id = 1
ORDER BY t.criada_em DESC;
```

### Total balance per user

```sql
SELECT
    u.id,
    u.nome,
    COALESCE(SUM(c.saldo), 0)::NUMERIC(14,2) AS valor_guardado
FROM usuarios u
LEFT JOIN contas c ON c.usuario_id = u.id AND c.ativa = TRUE
GROUP BY u.id, u.nome
ORDER BY valor_guardado DESC;
```

### Consistency check

The current stored balance must reconcile with transaction logs. This query flags accounts where the latest ledger balance (`saldo_apos`) does not match the active balance in `contas`.

```sql
WITH ultima_movimentacao AS (
    SELECT DISTINCT ON (conta_id)
        conta_id,
        saldo_apos
    FROM movimentacoes
    ORDER BY conta_id, criado_em DESC, id DESC
)
SELECT
    c.id,
    c.numero,
    c.saldo AS saldo_da_conta,
    u.saldo_apos AS saldo_da_ultima_movimentacao
FROM contas c
JOIN ultima_movimentacao u ON u.conta_id = c.id
WHERE c.saldo <> u.saldo_apos;
```

## 9. Compound interest simulation

The `simulacoes_juros` table is for learning and does not modify bank balances. For example, calculating a principal of R$ 1,000 at 5% monthly over 6 months:

```sql
SELECT
    1000.00 AS valor_inicial,
    1000.00 * POWER(1 + 0.05, 6) AS juros_compostos,
    1000.00 + (1000.00 * 0.05 * 6) AS juros_simples;
```

Approximate output:

- Simple interest: `R$ 1,300.00`
- Compound interest: `R$ 1,340.10`

Formulas:

```text
Simple interest:   M = P * (1 + i * n)
Compound interest: M = P * (1 + i)^n

P = principal
M = total accrued amount
i = interest rate per period (decimal)
n = number of periods
```

These mathematical simulations illustrate formula mechanics. They do not constitute investment yields or financial promotions.

## 12. Security and boundaries

- Never store passwords in plain text.
- Never commit database passwords, tokens, or API keys to Git.
- Use `CREATE USER` with minimum required privileges for application access.
- Always use HTTPS for external APIs.
- Validate inputs both in backend code and at the database constraint level.
- Use parameterized queries; never concatenate user input into raw SQL strings.
- Never expose `senha_hash` in API responses or public views.
- Store currency amounts in `NUMERIC`, not `FLOAT`.
- Distinguish between account balances, saving as an active habit, and traditional savings passbooks as retail products.
- Never use this project for real financial transactions.
